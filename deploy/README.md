# Absensa on Windows

This is an initial distribution foundation while Absensa is still under
development. It runs PostgreSQL, FastAPI, one notification scheduler, and the
WhatsApp bridge in Linux containers. Python, Node.js, libarchive and Chromium
are included in the images. Existing e-Rapor/Dapodik installations are independent;
Absensa does not use their databases, folders, runtimes or ports.

A graphical installer, published release images, automated backups/restores,
and unattended upgrades are future work. For now, a technical helper prepares
Docker once and runs the commands below from an extracted copy of the project.
Keep the same project folder/configuration for subsequent starts.

Validation here uses Linux Docker. The Windows Desktop/WSL2 and Hyper-V paths
still need a trial on the school's actual hardware, including LAN access and
recovery after restart. No Windows installer executable is included yet.

## Choose the host

| Host | Deployment path |
| --- | --- |
| Windows 10/11, 64-bit | WSL2 + Docker Desktop using Linux containers |
| Windows Server | Linux VM under Hyper-V or another supported hypervisor, then Docker Engine + Compose |
| Windows 8 | Not supported |

Use a Windows release still supported by Microsoft and your Docker version;
Windows 10 compatibility is conditional on that servicing status. Docker Desktop
is **not supported on Windows Server**. See the current
[Docker Windows requirements](https://docs.docker.com/desktop/setup/install/windows-install/).

Planning estimates for Absensa are 4 GB with limited headroom, 8 GB recommended,
and 16 GB comfortable when sharing a server with other school applications.
These are not measured capacity guarantees. Docker Desktop itself currently lists
8 GB host RAM as a prerequisite; the 4 GB estimate is not a supported Desktop
host recommendation. Windows, virtualization and Chromium usually consume more
than basic attendance processing. Prefer an SSD, wired Gigabit Ethernet and a UPS.
Allow several GB for images/build caches in addition to school data and backups.

## Windows 10/11 setup

1. Enable hardware virtualization in BIOS/UEFI. Install/update WSL2 following
   [Microsoft's instructions](https://learn.microsoft.com/windows/wsl/install).
   A prerequisite installation may request a reboot; schedule that around other
   school applications.
2. Install [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/),
   choose the WSL2 backend and Linux containers, and start it. No manually created
   Ubuntu VM is needed. Check Docker's licensing terms for your organization.
3. Extract the project into a local folder such as `C:\Absensa`. Open PowerShell
   there. Avoid a shared/network/synchronized folder for deployment secrets.
4. Check Docker, generate private settings, then build and start:

```powershell
docker info --format '{{.OSType}}'
docker compose version
# OSType must be linux. Configuration generation never replaces an existing file.
docker run --rm --mount "type=bind,source=$($PWD.Path)\deploy,target=/config" python:3.14-slim-bookworm python /config/configure.py
docker compose --env-file deploy/production.env -f compose.production.yml build
docker compose --env-file deploy/production.env -f compose.production.yml up -d --wait
docker compose --env-file deploy/production.env -f compose.production.yml exec web python -m scripts.create_admin admin
```

The last command prompts for the administrator password; it is not saved in
command history. It also resets the password if that username already exists.
Open `http://localhost:8088/admin`. Link WhatsApp using the admin dashboard's QR
code. An unlinked WhatsApp account does not prevent attendance from working.

Settings live in `deploy/production.env`, which is ignored by Git. The generator
creates independent random database and bridge secrets, never prints them, and
refuses to overwrite the file. Protect it with Windows file permissions so only
the deployment administrator can read it. Do not regenerate credentials after
the database volume has been initialized: changing the file does not rotate the
password inside PostgreSQL. Session tokens are already generated by the app and
stored server-side; no extra unused session signing secret is needed.

The default web port is **8088**. Change `ABSENSA_PORT` before starting if another
program uses it (or add `--port 8090` to the configuration generator). `TIMEZONE`
defaults to `Asia/Jakarta`; use `Asia/Makassar` or `Asia/Jayapura` when appropriate.
Do not combine this Compose file with `docker-compose.yml`: the latter is the
development database and publishes a database port.

## School LAN and Windows Firewall

Reserve a stable LAN address for the Windows PC. On a trusted **Private** network,
run the following once in Administrator PowerShell, replacing 8088 if needed:

```powershell
New-NetFirewallRule -DisplayName "Absensa web 8088" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8088 -Profile Private -RemoteAddress LocalSubnet
```

Allow only this web port. Do not open PostgreSQL or bridge ports. Existing firewall
rules still apply; verify from another school PC using, for example,
`http://192.168.1.10:8088/admin`. If the network uses a Domain profile or multiple
subnets, ask its administrator for an equivalent rule limited to the school LAN.
Do not disable the firewall or change a public network to Private indiscriminately.

Docker publishes the web port through Windows; there is no need to expose the
WSL VM's IP. Do not forward this port from the internet router. Default LAN HTTP
uses non-Secure cookies while retaining HttpOnly, SameSite, CSRF checks and all
existing authentication. Use only a trusted LAN. Optional HTTPS can be added
later: set `COOKIE_SECURE=true`, put a proxy in front, and explicitly configure
Uvicorn to trust forwarded headers only from that proxy so same-origin validation
sees the external HTTPS URL. Proxy trust is disabled in the default image.

Enable Docker Desktop startup at sign-in and prevent the PC from sleeping during
school hours. Container restart policies take effect only after Docker is running;
Desktop is not an unattended Windows boot service. Verify behavior after a planned
restart. For a server that must recover without interactive login, use the VM path.

## Windows Server setup (separate path)

Do not install Docker Desktop on Windows Server. Have the server administrator
create an Ubuntu Server 24.04 LTS VM using Hyper-V (or the existing supported
virtualization platform). A starting allocation is 2 vCPUs, 2–4 GB VM RAM and
30 GB disk, adjusted for Chromium, school size and host headroom. This is a trial
starting point, not a benchmark. Keep the Windows host's other software intact.

Use an external virtual switch connected to the school LAN and reserve a stable
IP **for the VM**. Configure automatic VM startup and graceful shutdown. Install
[Docker Engine and the Compose plugin](https://docs.docker.com/engine/install/ubuntu/)
inside the VM, and enable the Docker service at boot. Grant Docker access only to
the deployment administrator. Copy the project there, then in its root run:

```bash
python3 deploy/configure.py
docker compose --env-file deploy/production.env -f compose.production.yml build
docker compose --env-file deploy/production.env -f compose.production.yml up -d --wait
docker compose --env-file deploy/production.env -f compose.production.yml exec web python -m scripts.create_admin admin
```

Browse `http://VM-LAN-IP:8088/admin`; a firewall rule for the Windows host IP is
not a replacement for VM network rules. Restrict the VM web port to school LAN
sources using Docker-aware forwarding/firewall rules. Docker's published ports
can bypass ordinary UFW rules; see the firewall notes in Docker's Engine install
guide. SSH, if enabled for maintenance, should be limited to administrators.
The database is on an internal Docker network, and neither database nor WhatsApp
has a published host port.

## Starts, health and storage

```text
docker compose --env-file deploy/production.env -f compose.production.yml ps -a
docker compose --env-file deploy/production.env -f compose.production.yml logs --tail 100 web scheduler whatsapp migrate
```

On first startup, PostgreSQL becomes ready, `migrate` applies Alembic migrations
and exits successfully, then web and scheduler start. A migration failure blocks
those new services. `migrate` being Exited (0) is normal. FastAPI runs one worker
without reload, and the scheduler remains a separate single instance. Never scale
the scheduler or start another host scheduler against this database. Its existing
database delivery claims remain unchanged.

`/health` checks web/database readiness without exposing database details.
The bridge's private `/health` reports HTTP process liveness, not whether an
account is linked. Check connection state in the admin dashboard. Scheduler
monitoring in this foundation is process status and logs; a progress heartbeat
is deferred. Docker marks failed probes unhealthy but does not automatically
restart a still-running unhealthy process. Restart policies handle process exits.
Internet loss can interrupt WhatsApp while local attendance continues to work.

All service logs rotate at 10 MB with three files per container. Avoid sharing
full configuration or `docker inspect` output, which contains secrets.

| Named volume (default project `absensa`) | Contents |
| --- | --- |
| `absensa_pgdata` | PostgreSQL 18 data, including admin/device sessions and import previews |
| `absensa_photos` | Student profile photos |
| `absensa_whatsapp_auth` | Sensitive WhatsApp linked-device credentials |

Keep the Compose project name unchanged: changing it selects different volumes.
Ordinary `docker compose ... down`, recreation and image replacement preserve
volumes. **Never use `down -v` or volume prune on the deployed system** unless
deliberately destroying its data. Do not uninstall/reset Docker without backups.
WhatsApp's disposable web cache stays in the container; its authentication volume
persists. Chromium is installed inside the bridge, runs as a non-root user, and
keeps its sandbox enabled. Only that service receives `SYS_ADMIN`, needed for
Chromium namespace sandboxing under Docker (see
[Puppeteer's container guidance](https://pptr.dev/guides/docker)). This is a broad
capability and a deliberate initial compatibility tradeoff; no container runs
privileged or mounts the Docker socket. Review a tighter sandbox profile before
hardening this into a public release.

## Backup before changing versions

Use a fresh backup directory, stop writers so photos and database correspond,
dump PostgreSQL and copy files out. These commands work in PowerShell and bash
from the project root. They avoid binary shell redirection, which can corrupt
archives in older PowerShell versions.

```text
mkdir backup-2026-09-29
docker compose --env-file deploy/production.env -f compose.production.yml stop web scheduler
docker compose --env-file deploy/production.env -f compose.production.yml exec -T db pg_dump -U absensa -d absensa -Fc -f /tmp/absensa-backup.dump
docker compose --env-file deploy/production.env -f compose.production.yml cp db:/tmp/absensa-backup.dump backup-2026-09-29/database.dump
docker compose --env-file deploy/production.env -f compose.production.yml cp web:/app/photos backup-2026-09-29/photos
```

Check each command succeeds before proceeding. Copy `deploy/production.env`,
`compose.production.yml` and the matching source/release archive into the protected
backup and record the date and application version. Copy the backup to a different
physical disk and restrict access: it contains personal data, credentials and
database sessions. Keep backups outside the source repository. Delete the temporary
dump in the database container after verifying the external copy. If you are only
backing up, resume with `docker compose ... start web scheduler` (replace `...`
with the same `--env-file` and `-f` options above).

Do **not** include `whatsapp_auth` in a normal portable backup. Relink WhatsApp on
disaster recovery. A recovery requires a fresh isolated deployment using the saved
configuration/version, restoring `database.dump` with PostgreSQL 18 `pg_restore`
into an empty database, and copying photos back with ownership UID/GID 10001.
Keep web/scheduler stopped until both are restored, verify admin login and sample
photos, then relink WhatsApp. Restored database sessions can revive old logins;
invalidate them when recovery follows a compromise. Rehearse this with a separate
test deployment before entrusting real data; automated restore tooling is deferred.

## Updating this early distribution

Build replacement images before taking the existing app down. Keep the previous
source archive and backup. Set `ABSENSA_VERSION` to a new local image tag for each
snapshot so the old images remain available. This is a local image label, not
a promise that a matching image has been published to a registry.

1. Use the new source with the same private configuration and Compose project name.
2. Run `docker compose --env-file deploy/production.env -f compose.production.yml build`.
   A build failure leaves the existing containers running.
3. Back up the current deployment as above. Keep web/scheduler stopped.
4. Run `docker compose --env-file deploy/production.env -f compose.production.yml down`
   **without `-v`**, then `docker compose --env-file deploy/production.env -f compose.production.yml up -d --wait`.
5. Verify health, login, photos and scheduler logs before resuming school use.

The deliberate downtime ensures an old web/scheduler process is not running
against migrations for a new version; removing the old migration container also
ensures migrations run again. If migration or health checks fail, keep the app
stopped and inspect logs. Do not automatically run old code against a possibly
changed schema. Recovery is the previous source/images plus the matching
database/photos backup, rehearsed separately. There is no automatic rollback yet.
Never update the PostgreSQL major version as an ordinary image refresh: it needs
its own database migration procedure.

Initial builds need internet for base images and dependencies. After images have
been built and retained locally, ordinary starts and attendance require no cloud
service. For a disconnected site, a technical helper can build matching images
on another Linux-container machine and transfer them with `docker save/load`,
including `postgres:18.4-alpine`; generate unique site secrets separately and
start with `up -d --no-build --pull never`. Published, versioned image bundles
and a friendly installer can be added when the app's features settle.
